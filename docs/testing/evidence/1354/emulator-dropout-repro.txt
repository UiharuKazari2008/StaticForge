#1354: the Monitor dropout reproduced on an Android emulator with the Fold's app build, 27 Nov 2026.
NOT the Fold and not real hardware. The recorder and the server were not touched: what ONE test page received was faked.

RESULT
  BROKEN (the playlist stays at the one segment s393321, what the old recorder listed): the sound position advances for about
  10 s and stops. currentTime freezes (9.43 / 9.48), readyState 2, the element logs "waiting" at 9.8-10.1 s, hls.js logs
  bufferStalledError. It stays so to the end of the run (130 s and 110 s). Seen in both broken runs. The receiver reads
  ACQUIRING SIGNAL (read in run 2; run 1 did not open that tab).
  CONTROL (same segments, the playlist starts with 4 and gains one every 9.75 s): run 2 played the whole run with no
  "waiting" and no hls.js error: currentTime 10.54 -> 116.40 in 110 s of wall time (105.86 s of media, 0.96 of real time),
  one buffered range, never less than 15.7 s buffered ahead, receiver "playing" in all 45 samples.
  CONTROL run 1 was NOT clean and is kept below: currentTime always advanced and the receiver always read "playing", but from
  about 45 s it advanced at about 0.44 of real time (44.5 s -> 109.5 s: 51.57 -> 80.37), hls.js logged bufferStalledError
  (non-fatal) at 83.1 and 102.9 s and the element "waiting" -> "playing" for 0.2 s at 102.9 s, with 16.7 s or more buffered
  ahead throughout, so the playlist had not run out. The harness's answers also slowed then (0.1 s -> up to 1.3 s). Cause NOT
  proven: Ruiko's CPU was not measured in run 1. Run 2, same method, measured Ruiko at 55-100 % and only had single
  samples down to 0.73 of real time.

WHAT WAS REAL
  The app build; the page, its XM Radio program and window.wmXmRadio.monitor(rid); hls.js; the WebView's audio element.
  The audio: saved segments s393321.aac onward of recording 40449d6a38bc1d17b4fd11d3 (read only, copied to a scratch
  folder, byte-identical). EXTINF and PROGRAM-DATE-TIME come from its segs.ndjson (its gap row is left out).
  Tags between frames in those files: 393322 after 369 of its 420 AAC frames, 393323 after 143 of 420. Both control runs
  played past both places (media time about 18.3 s and 22.8 s).
  The receiver's channel and song texts are the live feed for channel 53, not the audio being played.

WHAT WAS FAKED (inside this one page, over Chrome DevTools)
  1. Every request for /api/xmradio/rec/<rid>/* was answered by the harness (Fetch.enable on that URL pattern, service
     worker bypassed, cache disabled). The playlist has the lines playlist() in modules/xmRadioRecorder.js writes:
     EVENT, VERSION 6, TARGETDURATION 10, MEDIA-SEQUENCE 393321, START TIME-OFFSET=-30,PRECISE=NO, PROGRAM-DATE-TIME and
     EXTINF per segment, no ENDLIST. All answers went with Cache-Control no-store (the server lets segments be cached).
     A segment not listed would have been answered 404; none was asked for.
  2. The listing. No recording was in progress (deck: recordings, queue, jobs and timers empty before and after the runs).
     NO test recording was started: a server recording is pushed to every phone's status (modules/phoneStatus.js, xmrec),
     so it would have shown the tape icon on the Fold, filed audio on a tape and held the only signed-in recorder slot.
     Instead this page's own answer to xmradio_deck_get got one extra entry with the made-up rid e11354000000000000000354
     (channel 53). The same wrapper refused any tune or any XM packet that changes something from this page. In broken
     run 1 it also refused one read, xmradio_tape_tracks (pattern too wide, narrowed afterwards); nothing else was refused
     in any run. After each run the wrapper was removed and the made-up entry was gone from the page's list.
  3. Hooks that only observe: HTMLMediaElement.prototype.play (the audio element is not in the document) and
     Hls.prototype.attachMedia (to log hls.js errors). hls.js was loaded just before Monitor instead of by Monitor.
  The broken playlist is a replay of server-dropout-replay.txt (one segment listed for the first 170 s there). The hole at
  128 s and what a listener gets when the old recorder's playlist grows again were NOT simulated.

WHICH PLAYER
  In every sample of every run AndroidVideos.state() (the app's native player) was "off", and the page called play() on its
  own audio element: wmXmRadio does that only when the native handOff() did not answer true. The rejection itself was not
  seen in a log (no player line from the app).
  dumpsys audio, 14 s into each run: one AAudio player of the app's process (uid 10217, pid 5755), state started,
  USAGE_MEDIA, muted by volume. At 48 s it was still there in both control runs and gone in both broken runs.
  dumpsys media_session showed no playback state for the app; navigator.mediaSession is absent in this WebView.
  lane.sh sound over each of the four runs: no notification sound (count 0), alarmLikeStarted 0.
  Nothing was listened to: the proof is the element's position and state, not audio heard.

HOW TO READ THE TABLES
  t = seconds after monitor(rid) (this server's clock; event times use the page's clock from the same call; broken run 1 did
  not measure the offset between the two clocks, so its event times are corrected with the 10.87 s measured later). ct = audio.currentTime;
  rs = readyState (4 enough data, 2 only the current frame); bufEnd = end of the last buffered range; receiver = data-state
  of the XM receiver on Now Playing; listed = segments in the last playlist; reqs = requests answered so far.
  The control starts near ct 9 because the playlist asks to start 30 s behind its end.
